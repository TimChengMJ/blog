什么是 LIN？
LIN（Local Interconnect Network）是一种低成本、单线、主从式串行通信协议，专为汽车车身舒适性功能设计。它由 LIN 联盟（LIN Consortium，BMW、Daimler、Motorola、Volvo 等联合制定）于 1999 年发布，以极低的实现成本（仅需标准 UART + 单线收发器）连接 ECU 与低速传感器/执行器。
LIN 在汽车网络中的定位

LIN 是 CAN 的有效补充，专注于低成本、低速率的本地互联。典型应用于车门、座椅、车窗、空调等舒适性子系统。

Schedule Table
调度表机制
Master 调度逻辑、Frame Slot 计算与调度表切换
调度表原理

LIN Master 按照预定义的调度表（Schedule Table）循环发送帧 Header。调度表由若干 Frame Slot 组成，每个 Slot 指定：要发送的帧 ID 和该 Slot 的时间长度（Frame Slot Time）。

Frame Slot Time 计算：
T_frame_slot ≥ T_header + T_response + T_jitter
其中：T_header = 34 位时间 + IFS（Break 13位+Delim+Sync 10位+PID 10位）
T_response = (N_data + 1) × 10 位时间（N_data 字节数据 + 1 校验和字节）
典型 20kbps、8字节数据帧：T_frame_slot ≈ 5.2ms，通常配置为 6~8ms 留余量
调度表 LDF 示例
/* LDF 调度表定义示例 */
Schedule_tables {
  /* 正常运行调度表 */
  NormalTable {
    WindowMotor_Status  delay 10 ms;   /* 车窗电机状态，10ms 周期 */
    SeatPosition_Read   delay 20 ms;   /* 座椅位置读取，20ms 周期 */
    ClimateControl_Cmd  delay 20 ms;   /* 空调控制指令，20ms 周期 */
    DoorStatus_Read     delay 50 ms;   /* 门状态读取，50ms 周期 */
  }
  /* 诊断调度表（访问 NAD=0x01 的 Slave） */
  DiagTable {
    MasterReq           delay 10 ms;   /* 0x3C 主请求帧 */
    SlaveResp           delay 10 ms;   /* 0x3D 从响应帧 */
  }
  /* 初始化/配置调度表 */
  InitTable {
    AssignNAD_req       delay 10 ms;
    AssignNAD_resp      delay 10 ms;
  }
}
调度表切换机制
1
正常模式（Normal Schedule）
系统上电后进入正常调度表，循环发送应用数据帧，覆盖所有 Slave 节点的周期性数据
2
诊断模式（Diagnostic Schedule）
上层（ComM/Dcm）发起诊断请求时，Master 切换到诊断调度表，交替发送 0x3C/0x3D 帧，完成诊断后回切
3
初始化/配置调度（Init Schedule）
系统首次上电或节点更换时，运行 AssignNAD、AssignFrameId 等配置帧序列
4
事件触发冲突解析（Collision Resolving）
ETF 发生冲突时，Master 临时切换到冲突解析调度表，逐一查询各 Slave 的无条件帧
偶发帧（Sporadic Frame）在调度表中的处理

偶发帧（Sporadic Frame）在调度表中占据固定 Slot 位置，但 Master 仅在对应信号数据发生变化时才实际发送 Header，否则跳过该 Slot。这可以在保持调度表结构不变的前提下节省总线带宽。

Sporadic Frame 配置要点：
• 在 LDF 的 Sporadic_frames 块中声明，并关联一组"候选无条件帧"
• Master 在每个调度周期检查所有候选帧的信号是否有更新，若有更新则发送变化最早的那帧
• 若同一 Slot 内多帧均有更新，本次发最高优先级帧，其余等下一轮
• LinIf 通过 Lin_HeaderIndication() 回调通知上层，由上层决定是否提供 Response 数据

Transport Layer
传输层 (LIN TP)
多帧诊断传输、PDU 格式与流控机制
LIN TP 概述

LIN 传输层（LIN TP / LIN Transport Protocol）基于 ID=0x3C（MRF）和 ID=0x3D（SRF）的 8 字节诊断帧，实现超过 6 字节的多帧数据传输，用于 UDS 诊断、节点配置等服务。

PDU 类型
PDU 类型NAD Byte[0]PCI Byte[1]含义
SF (Single Frame)NAD0x0N（N=数据长度1~6）单帧，最多 6 字节有效数据
FF (First Frame)NAD0x1N + Byte[2]=LEN多帧首帧，Byte[1]低4位+Byte[2]=总长度
CF (Consecutive Frame)NAD0x2N（N=序号1~F,0）多帧后续帧，序号循环，最多 6 字节/帧
LIN TP vs CAN TP：LIN TP 没有 Flow Control（FC）帧，Master 通过调度表控制 CF 帧的发送时机，无需显式流量控制。这简化了实现，但也意味着每次请求/响应之间必须通过调度表留足时间窗口。
MRF / SRF 帧格式（8字节）
/* Master Request Frame (ID=0x3C) 格式 */
Byte[0] = NAD          /* 目标 Slave 节点地址（1~125）*/
Byte[1] = PCI          /* 0x06=单帧，0x10/11=首帧，0x21~=续帧 */
Byte[2] = LEN/SID      /* 单帧:数据长度；多帧首帧:高字节；其余=SID */
Byte[3..7] = DATA      /* 有效数据载荷 */

/* Slave Response Frame (ID=0x3D) 格式 */
Byte[0] = NAD          /* 响应的 Slave 地址 */
Byte[1] = PCI          /* 同上 */
Byte[2] = LEN/RSID     /* RSID = SID | 0x40 */
Byte[3..7] = DATA      /* 响应数据 */
Master / Slave
Master / Slave 节点
主从节点职责划分与任务分工
Master 节点职责
调度表执行
按预定义调度表循环发送 Header（Break+Sync+PID），驱动整个总线通信节奏
时钟提供
通过 Break+Sync 为所有 Slave 提供同步时钟基准，Slave 无需精确晶振
网络管理
负责 Slave 的 NAD 分配、帧 ID 分配、唤醒/休眠控制
错误监测
监测 Response 超时、校验和错误，上报给上层并决策是否重试
诊断转发
作为 LIN-CAN 网关，将 CAN 侧的 UDS 诊断请求转发到 LIN 子网
Slave 节点职责
波特率自适应
通过测量 Sync 字节的下降沿间隔，自动计算并适应当前波特率，无需配置
PID 过滤
收到 Header 后比较 PID（含奇偶校验），判断自己是否需要发送或接收该帧
Response 发布
若自己是 Publisher，在规定时间内发送 Response（数据+校验和）
Response 订阅
若自己是 Subscriber，接收并校验 Response 数据，更新本地信号值
诊断服务
响应 NAD 寻址的诊断请求（AssignNAD、ReadByID、UDS 服务等）
Master Task 与 Slave Task
概念属于说明
Master Task任意节点负责发送 Header 的任务。通常只有 Master 节点运行 Master Task
Slave Task任意节点负责处理 Header 并决定是否发送/接收 Response 的任务。所有节点（含 Master）都运行 Slave Task
Master 节点也运行 Slave Task，因此 Master 也可以作为某些帧的 Publisher 或 Subscriber。当 Master 发布 Response 时，Header 和 Response 都由 Master 自己完成——这称为 Master 自回环帧，用于向 Slave 广播控制指令。

LIN UDS 诊断（通过 LIN TP 传输）
LIN 诊断体系

LIN 的诊断通过 LIN TP（传输层） 承载 UDS（ISO 14229）服务，与 CAN 侧的 UDS 诊断原理相同，但受限于 LIN 的 8 字节帧和 20 kbps 速率，诊断吞吐量较低。

0x11ECUReset复位 LIN Slave，Slave 复位后重新执行初始化
0x22ReadDataByIdentifier读取 Slave DID，数据若超 6 字节需分多帧传输

System Design
系统设计方法
从需求到实现的完整 LIN 网络设计流程
LIN 系统设计流程
01
功能需求分析
梳理 LIN 子系统的功能（车窗控制、座椅调节等），确定需要传输的信号列表：信号名、方向（M→S 或 S→M）、数据类型、更新频率、精度
02
节点清单与 NAD 分配
确定 Slave 节点数量（≤16），分配 NAD（1~125，推荐按功能域分段）。明确每个节点的 Supplier ID 和 Function ID（唯一标识 Slave 类型）
例：车窗左前 NAD=0x01, 右前=0x02, 左后=0x03, 右后=0x04
03
帧与信号设计
将信号打包到帧中（同一帧的信号共享 Publisher），设计帧 ID（0x00~0x3B），确定每帧数据长度（1/2/4/8 字节）和信号位域布局
04
调度表设计
根据信号更新频率和时延要求，设计 Frame Slot Time 和调度周期。优先级高/频率高的帧给更小的 Slot 时间，低优先级帧可以用倍数关系跳过
05
编写 LDF 文件
将以上设计输出为标准 LDF 文件，包含：nodes, signals, frames, schedule_tables, node_attributes 等完整定义
06

完整 LDF 示例（车窗控制子系统）
LIN_description_file;
LIN_protocol_version = "2.2";
LIN_language_version = "2.2";
LIN_speed = 20 kbps;

/* 节点声明 */
Nodes {
  Master: BCM, 5 ms, 0.1 ms;    /* 主节点 BCM，调度精度5ms，抖动0.1ms */
  Slaves: WinMotorLF, WinMotorRF;  /* 左前/右前车窗电机 Slave */
}

/* 节点属性 */
Node_attributes {
  WinMotorLF {
    LIN_protocol = "2.2";
    configured_NAD = 0x01;
    initial_NAD = 0x7F;
    product_id = 0x0026, 0x0001, 0x00; /* Supplier=0x0026, Function=0x0001 */
    response_error = WinLF_RespErr;
    P2_min = 50 ms;
    ST_min = 0 ms;
    configurable_frames {
      WinMotor_LF_Cmd  = 0x01;  /* 指令帧 ID 0x01 */
      WinMotor_LF_Sts  = 0x11;  /* 状态帧 ID 0x11 */
    }
  }
  WinMotorRF {
    configured_NAD = 0x02;
    initial_NAD = 0x7F;
    product_id = 0x0026, 0x0002, 0x00;
    /* ... 同上 ... */
  }
}

/* 信号定义 */
Signals {
  WinLF_PosCmd:    8, 0,  BCM,        WinMotorLF;  /* 位置指令, 8bit */
  WinLF_SpeedCmd:  4, 0,  BCM,        WinMotorLF;  /* 速度指令, 4bit */
  WinLF_Position:  8, 0,  WinMotorLF, BCM;          /* 实际位置反馈, 8bit */
  WinLF_Current:   8, 0,  WinMotorLF, BCM;          /* 电机电流, 8bit */
  WinLF_Status:    4, 0,  WinMotorLF, BCM;          /* 运行状态, 4bit */
  WinLF_RespErr:   1, 0,  WinMotorLF, BCM;          /* 响应错误标志 */
}

/* 帧定义 */
Frames {
  WinMotor_LF_Cmd: 0x01, BCM, 2 {    /* Master→Slave, 2字节 */
    WinLF_PosCmd,  0;                  /* 位置指令 Byte0 全部8位 */
    WinLF_SpeedCmd, 8;                 /* 速度指令 Byte1 低4位 */
  }
  WinMotor_LF_Sts: 0x11, WinMotorLF, 4 {  /* Slave→Master, 4字节 */
    WinLF_Position, 0;
    WinLF_Current,  8;
    WinLF_Status,   16;
    WinLF_RespErr,  20;
  }
}

/* 信号编码 */
Signal_encoding_types {
  WinPosition_Encoding {
    logical_value, 0x00, "CLOSED";
    logical_value, 0xFF, "OPEN";
    physical_range, 1, 254, 0.392, 0; /* 1~254 → 0.4%~100% */
  }
}
Signal_representation {
  WinPosition_Encoding: WinLF_Position, WinLF_PosCmd;
}

/* 调度表 */
Schedule_tables {
  NormalSchedule {
    WinMotor_LF_Cmd  delay 10 ms;
    WinMotor_LF_Sts  delay 10 ms;
    WinMotor_RF_Cmd  delay 10 ms;
    WinMotor_RF_Sts  delay 10 ms;
  }
  DiagSchedule {
    MasterReq  delay 10 ms;
    SlaveResp  delay 10 ms;
  }
}

LIN 休眠机制

LIN 没有独立的网络管理协议，休眠由 Master 通过发送睡眠命令帧（Go-to-Sleep Frame）触发，唤醒通过检测总线唤醒脉冲实现。

Go-to-Sleep Frame：是一个特殊的无条件帧（ID=0x3C，即 MRF），其 Response 由 Master 自己发送，内容为固定字节 [0x00, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF]（NAD=0x00 为广播）。所有 Slave 收到此帧后进入睡眠模式。
唤醒与休眠完整时序
Slave 主动唤醒（可选）
某些 LIN 规范允许 Slave 主动发送唤醒脉冲（例如 Slave 检测到按钮按下后触发总线唤醒）。Slave 唤醒脉冲长度为 250μs~5ms 的显性信号。Master 检测到总线活动后进入正常调度流程，并在确认总线活跃后开始发送 Header。

Application Scenarios
典型应用场景
LIN 在汽车各子系统中的具体应用
场景一：车门控制模块（DCM）
典型配置：BCM 作为 LIN Master，车门控制 ECU（DCM）作为 Slave（NAD=0x01~0x04，对应左前/右前/左后/右后）。
信号列表：车窗位置（0~100%）、升降速度、防夹力反馈、门锁状态、门把手检测、后视镜角度（H/V）
调度设计：车窗控制帧 10ms 周期（实时性要求高），门锁状态帧 50ms 周期（低频监测），后视镜 20ms 周期
波特率：20 kbps，总节点：4 个 Slave，调度表总周期约 40ms
场景二：雨刮系统
典型配置：BCM 作为 Master，雨刮传感器（雨量传感器 + 光线传感器）作为 Slave。
信号：雨量值（0~255）、光线强度、雨滴检测状态、建议雨刮速度（0=停、1=慢、2=快、3=间歇）
特点：传感器仅有读取需求，所有帧均由 Slave 发布（S→M 方向），Master 定期轮询。
调度：单一调度表，20ms 周期，帧极少（2~3帧），总线利用率 <15%
场景三：智能前大灯（AFS）
典型配置：BCM/前大灯控制 ECU 作为 Master，左右光源控制 Slave（各 1 个，NAD=0x01/0x02）。
信号：灯光亮度（PWM占空比）、近光/远光/雾灯状态、光源温度、故障标志
LIN 优势：单线连接大幅减少灯组内部布线，灯泡直接集成 LIN Slave 芯片（ATA6625Q 等）
特殊需求：需要 ReadByIdentifier 读取光源序列号以支持更换追踪
场景四：座椅控制（Memory Seat）
典型配置：BCM/座椅控制 ECU 作为 Master，多个执行器 Slave（前后滑动、靠背、高度、腰托）
信号：各轴位置反馈（8bit 分辨率）、目标位置指令、运动速度、限位开关状态
记忆功能：通过 SaveConfiguration 服务将位置数据固化到 Slave NVM，支持多用户记忆
节点数：通常 4~8 个 Slave，调度表设计需要仔细分配 Slot 时间避免运动延迟
场景五：空调 HVAC 系统
典型配置：HVAC 控制 ECU 作为 Master，风门执行器、温度传感器、风机调速模块等作为 Slave
信号：风门开度（0~100%）、出风方向、温度传感器值（内/外/蒸发器）、风机转速
特点：HVAC 内部使用 LIN 实现系统集成，对外通过 CAN 与 BCM 交互
电源管理：空调 LIN 子网通过独立 Sleep/Wake 控制，不受整车 CAN NM 直接影响
Error Handling
错误处理
LIN 通信错误类型、检测机制与处理策略
LIN 错误类型
错误类型触发条件检测方处理策略
Bit Error发送位与回读位不匹配（总线冲突）发送方自监听停止发送，上报错误，等待下次调度
Checksum Error收到的校验和与计算值不符接收方（Master/Subscriber）丢弃数据，Master 记录 Frame Error，超限报 DTC
Response ErrorSlave 未在规定时间内发送 ResponseMaster 超时检测Master 标记该帧为 No Response，通知 LinSM
Framing Error停止位不为 1，或字节格式错误UART 硬件检测丢弃该字节，尝试重同步
Sync Break ErrorBreak 长度不足（<11位）或同步失败SlaveSlave 忽略该帧，等待下一个 Break
Parity ErrorPID 奇偶校验失败Master + Slave忽略该帧，Master 重新发送 Header
Response Error 信号
每个 LIN Slave 在 LDF 的 Node_attributes 中声明一个 response_error 信号（1 bit）。当 Slave 检测到传输错误（自己发送 Response 时 Bit Error 或 Framing Error）时，将 response_error bit 置 1 并随下一个 Response 一起发送。Master 读取此 bit 并上报给应用层，用于 DTC 判断和诊断。
错误处理策略
1
单次错误容忍
偶发性 Checksum Error 或 Response Timeout 不立即报故障，先重试（下次调度自动重发 Header）
2
连续错误计数
若同一帧连续 N 次（通常 3~5 次）出现错误，将该 Slave 标记为"通信失败"，上报 DTC，并通知上层应用切换到降级模式
3
降级模式
失联 Slave 对应功能采用默认值（如车窗停止控制、座椅保持当前位置）；Master 继续发送 Header（为了后续恢复时能够重新通信）
4
自动恢复
若失联后某次 Slave 正常响应，清除错误计数，取消降级模式，通知应用层"节点恢复"

Frame Slot Time 计算公式
/* Frame Slot Time 计算（位时间 = 1 / 波特率） */
T_bit  = 1 / 20000 = 50 μs  （20kbps）

T_header = (1 + 13 + 1 + 10 + 10) × T_bit  /* 停顿+Break+Delim+Sync+PID */
         = 35 × 50μs = 1.75ms

T_response = (N_data + 1) × 10 × T_bit      /* 数据字节数+1(校验) × 10位帧 */
           = (8 + 1) × 10 × 50μs = 4.5ms   （8字节数据）

T_frame_min = T_header + T_response = 1.75 + 4.5 = 6.25ms
T_frame_slot = T_frame_min × 1.4   ≈ 8.75ms  （留14%余量）

/* 不同数据长度的 Response 时间 */
N=2: T_resp = 1.5ms  → T_slot ≈ 4.5ms
N=4: T_resp = 2.5ms  → T_slot ≈ 6.0ms
N=8: T_resp = 4.5ms  → T_slot ≈ 8.75ms
