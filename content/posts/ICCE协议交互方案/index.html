SECTION 02
ICCE vs CCC 关键差异
对比维度ICCE（华为主导，国内）CCC（苹果/宝马，国际）
密钥体系✅ 对称密钥（AES）· 实现简单非对称密钥（ECDSA）· 安全性更强
认证方式挑战应答生成 SessionKey，双向认证SPAKE2+ 协议建立安全通道，标准交易/快速交易
BLE 定位BLE 主节点 + 多辅节点（RSSI/AoA/HADM）BLE + UWB 融合，UWB 厘米级精度
车端规范✅ 规范涵盖车端实现细节，推荐 SE规范不含车端实现
开发难度✅ 简单，开发成本低，协商空间大复杂，规范完整详细，互操作性强
生态现状✅ 国内 26+ 车企，200+ 车型，占比 45%+宝马/奔驰等高端车型，国内渗透率低
换手机体验✅ 云端同步，换手机较方便需重新授权配对
ℹ ICCE 规范对部分关键流程（如车主首次配对细节、借车人首次交易）描述不够完整，各厂家实现存在差异，实际开发中需主机厂、手机厂商、云平台、卡商四方协商确定实现细节。
SECTION 03
推荐技术组合方案
🥇 BLE + UWB（推荐）
BLE 负责连接、认证、粗定位（RSSI）；靠近车辆约 10~15m 后启动 UWB 精确测距，厘米级定位，防中继能力最强。适合旗舰车型。问界 M9 首发此方案。
🥈 BLE（主流基础方案）
纯 BLE 方案，基于 RSSI 多锚点定位，成本低，覆盖广。PEPS 精度约 0.5m 以内，遥控距离 ≥15m。上汽名爵 2021 年首发 ICCE 蓝牙无感数字钥匙。
🔒 NFC（备用降级方案）
NFC 直接路由到 SE Applet，安全性极高，不依赖蓝牙连接。作为 BLE 故障备份。比亚迪 2020 年率先使用 ICCE NFC 数字车钥匙。

ICCE Data 透传文本帧格式（§7.2.3）
所有 BLE 数据均封装在此帧格式中，采用小端序。Request 和 Response 必须成对出现，超时最多重试 3 次（同步）。

0=不分包

注：Length = Control(1B) + FSN(1B) + MessageID(1B) + CommandID(1B) + Payload(NB) 的总字节数，不含 Checksum(2B)。Ack 类 Response 的 Body 为空。

Control 字段 8 bit 详解
Bit[1:0] · 分包指示
00 完整包（不分包）
01 首帧（起始分帧）
10 过程帧（中间帧）
11 末帧（最后分帧）

过程帧和末帧 Body 直接填分段数据，不含 MessageID/CommandID
Bit[2] · 响应方式
0 同步响应
Response 含处理结果
超时最多重试 3 次

1 异步响应
先回 Ack 表示收到
执行完成后再发 Notify
Bit[3] · 加密指示
0 不加密（BLE 链路层已加密）

1 应用层二次加密
算法：AES-128-CBC
填充：ISO9797-M2
固定 IV：session IV
随机 IV：在FSN与MessageID间插入明文 TLV（首包）
Bit[4] · 方向指示
0 Response（应答）

1 Request（请求）

Bit[7:5] 预留 RFU

示例：0x10 = Request + 同步 + 不加密 + 完整包

SECTION 07
SE 安全单元与 APDU 工作原理
ICCE 认证本质上是基于智能卡技术（JavaCard / ISO7816-4）的对称密钥挑战应答方案。理解 SE 和 APDU 是实现握手认证的基础。
🔐 安全单元（SE）的形态
SE 是防篡改硬件安全部件，保证密钥的安全性与机密性。在 ICCE 体系中：

手机端：eSE（嵌入式，最安全）/ inSE（集成 SoC）/ SIM/UICC（运营商）/ microSD。支持 GlobalPlatform 规范，运行 JavaCard Applet。

车端：SE 或 HSM（硬件安全模块）。TEE 被视为软件密码模块，在国内商密认证中不等同于硬件密码模块，推荐使用 SE。
☕ JavaCard Applet 角色
Applet 运行于 JavaCard VM 上，不能自启动，由外部终端通过 SELECT(AID) 命令激活。ICCE 方案中需两端各一个 Applet：

手机端 Applet 需实现：
Select / GetProcessData / Auth / ReadBinary / UpdateBinary / Encrypt / Decrypt

车端 Applet 需实现：
Select / IntAuth（内部认证）/ ExternalAuth（外部认证）/ Decrypt
APDU 命令格式（ISO 7816-4）
字段长度说明示例值
CLA1B命令类别字节：0x00=标准指令集，0x80=安全指令集0x80
INS1B指令码，标识具体操作（如 0xCA=GetData，0xF2=Auth）0xCA
P11B参数1，指令的第一个限定参数0x00
P21B参数2，指令的第二个限定参数0x00
Lc0/1/3BData Field 长度（可选）0x32(50B)
Data0~65535B命令数据（可选）TLV 格式数据
Le0/1/3B期望响应数据长度（可选）0x00=最大

Response APDU = [Data Field] + SW1(1B) + SW2(1B)，其中 SW=9000 表示成功。

ICCE 密钥认证流程（对称挑战应答）
ℹ ICCE 认证本质是最常见的对称密钥挑战应答方案：双端共享同一对称密钥（通过 OEM 云开通时下发），使用随机数作挑战码，对方用共享密钥计算应答，发起方验证应答值，完成双向认证并生成 SessionKey。
APDU 流程（伪序列） // Step 1: Framework → SE Applet 发送 SELECT 选中 Applet SELECT(AID) → SW=9000 表示 Applet 就绪 // Step 2: 车端发 Auth Request（GetProcessData） // C-APDU: CLA=0x80 INS=0xCA P1=0x00 P2=0x00 Le=0x32 // 封装在 ICCE 帧 Msg=0x01 Cmd=0x01 中发给手机 Framework 车端 → 手机: GetProcessData(APDU) → Framework 拆封 → SE 处理 // Step 3: SE Applet 处理，生成本端随机数 RND_ICC SE Applet: 生成随机数 RND_ICC，准备挑战数据 手机 → 车端: GetProcessData Response(RND_ICC + 设备信息) // Step 4: 车端生成随机数 RND_IFD，用共享密钥 SK 计算认证码 车端: 生成 RND_IFD，用 SK 计算 MAC(RND_IFD || RND_ICC) // Step 5: 车端发 External Auth（外部认证），携带 RND_IFD + MAC 车端 → 手机: ExternalAuth(RND_IFD, MAC_车端) SE Applet: 用 SK 验证 MAC_车端 → 车端认证通过 SE Applet: 计算 MAC_手机(RND_ICC || RND_IFD) → 返回 // Step 6: 车端验证手机端 MAC（双向认证完成） 车端: 验证 MAC_手机 → 手机认证通过 // Step 7: 双端派生 SessionKey（用于后续加解密） SessionKey = KDF(SK, RND_IFD, RND_ICC) ← 两端分别计算，结果相同
⚠ ICCE 规范对认证流程中具体的密钥派生算法（KDF）、MAC 算法、APDU 具体格式等细节描述不完整，各主机厂、手机厂商需四方协商确定，这是 ICCE 落地时最大的挑战点之一。

安全设计详解
🔒 四层安全防护体系
层1 · BLE 链路层加密
配对后 LTK 进行链路层 AES 加密，防窃听。对等所有 BLE 数据。§5.2.3 Step9
层2 · 应用层二次加密（可选）
Control.Bit3=1，对 Body 内容进行 AES-128-CBC（ISO9797-M2 填充），关键业务指令建议开启。§7.2.3
层3 · SE 内密钥管理
SessionKey 在 SE 内生成和使用，不对外导出，蓝牙会话断开立即销毁。§6.1 条e
层4 · APDU 业务级双向认证
基于对称密钥挑战应答，通过 SE Applet 完成双向身份验证，生成 SessionKey。§7.3.1

密钥生命周期管理
LTK（长期密钥）生命周期
生成：配对时由双方 BLE 协议栈协商生成
保存：绑定后持久保存（手机 BLE 协议栈 + 车端）
用途：每次重连时直接用于链路层 AES 加密
销毁：数字钥匙失效时，车辆可清除配对关系（§5.2.3）
注意：若使用随机地址，配对和广播须使用相同 IRK（§6.2.1 条l）
SessionKey（会话密钥）生命周期
生成：每次握手认证时在 SE 内部生成，两端各自派生
作用域：仅当次 BLE 会话有效
用途：RKE 车控指令加解密 + 可选的应用层二次加密
销毁：蓝牙会话断开时立即清除（§6.1 条e）
丢失处理：手机感知 SessionKey 丢失时，通过 Notification(0x01, Event=0x02) 通知车辆重新握手

工程实现指南
Android 手机端实现要点
  • ✓BLE 扫描：BluetoothLeScanner，后台保活用 ForegroundService + WakeLock，占空比 ≥ 10%
  • ✓GATT Client：BluetoothGatt，连接后立即 discoverServices，找到 0xFFFD/0xFFFE
  • ✓开启通知：setCharacteristicNotification(0xFFFE, true) + 写入 CCCD Descriptor
  • ✓SE 访问：OMAPI（StrongBox / eSE），通过 SEService 获取 Reader → Session → Channel
  • ✓Passkey：BluetoothPairingCallback 处理 PAIRING_VARIANT_PASSKEY，车主也可自动填充但需用户确认
  • ✓定位广播：AdvertisingSet API (Android 8+)，使用 AdvertisingSetParameters 设置 RPA
  • ⚠后台 BLE 广播在 Android 12+ 需要 BLUETOOTH_ADVERTISE 权限，注意运行时申请
  • ●定位广播在亮屏/熄屏/锁屏场景必须行为一致，功率波动 ≤ ±2dB
iOS / watchOS 手机端实现要点
  • ✓BLE Central：CBCentralManager，后台扫描需 CBCentralManagerOptionRestoreIdentifierKey
  • ✓发现服务：peripheral.discoverServices，找 0xFFFD/0xFFFE Characteristic
  • ✓安全存储：Secure Enclave（P-256），或 KeyChain + CryptoKit 进行 AES 加解密
  • ✓背景广播：CBPeripheralManager，iOS 后台 advertise 有限制，需处理 truncated payload
  • ⚠iOS 后台 BLE 扫描受限，需监听 CoreBluetooth 的 state restoration 回调
  • ⚠iOS 不直接支持 Passkey Entry 配对的完整控制，BLE 配对流程需特殊处理
  • ●Apple Watch 可作为钥匙端，支持 BLE + NFC，需单独适配 watchOS API
帧构建与发送核心代码
Python（伪码） import struct, binascii def crc16_ccitt(data: bytes) -> int: """CRC16-CCITT (0xFFFF 初始值, 0x1021 多项式)""" crc = 0xFFFF for byte in data: crc ^= (byte << 8) for _ in range(8): crc = ((crc << 1) ^ 0x1021) if (crc & 0x8000) else (crc << 1) return crc & 0xFFFF def build_tlv(tag: int, value: bytes) -> bytes: """构建 TLV 格式数据""" return bytes([tag, len(value)]) + value def build_icce_frame(msg_id: int, cmd_id: int, payload: bytes, is_req=True, encrypt=False, async_rsp=False) -> bytes: body = bytes([msg_id, cmd_id]) + payload ctrl = 0x00 if is_req: ctrl |= (1 << 4) # Bit4=1: Request if encrypt: ctrl |= (1 << 3) # Bit3=1: AES-128-CBC if async_rsp:ctrl |= (1 << 2) # Bit2=1: 异步响应 length = 1 + 1 + len(body) # ctrl + fsn + body header = bytes([0x5A]) + struct.pack('<H', length) + bytes([ctrl, 0x00]) raw = header + body crc = crc16_ccitt(raw) return raw + struct.pack('<H', crc) # 使用示例：发送 RKE 获取随机数请求 payload = build_tlv(0x01, bytes([0x01])) # Type=Unlock frame = build_icce_frame(0x02, 0x04, payload) ble_write(char_uuid=0xFFFD, data=frame) # Write to ICCE Data In
