§ 01

背景与动机：蓝牙隐私保护的必要性

蓝牙低功耗（BLE）设备在广播时会持续对外发送本机 MAC 地址。若使用固定的公开地址，攻击者可轻易对特定设备进行长期追踪——无论是记录用户每日通勤路线，还是在商场中绘制个人活动轨迹，固定 MAC 地址都将成为严重的隐私漏洞。

⚠
威胁场景

攻击者在公共场所部署多个 BLE 监听节点，通过固定 MAC 地址关联同一设备的广播，可实现用户位置跟踪、行为分析，乃至设备指纹识别。

蓝牙核心规范在 4.0 版本引入了私有地址（Private Address）机制，并在 4.2 版本强化了可解析私有地址（Resolvable Private Address, RPA）。其核心思路是：

  • 设备广播时使用随机生成的临时地址，每隔一定时间（默认 15 分钟）轮换一次
  • 已配对的可信设备持有 IRK（Identity Resolving Key），可以从该随机地址中"认出"对方
  • 未持有 IRK 的第三方无法将前后两次广播关联到同一设备
✓
设计目标

在隐私性（对陌生人不可追踪）与可用性（对已配对设备可识别）之间取得平衡，同时不依赖在线服务器，纯本地运算即可完成解析。

§ 03

RPA 地址结构详解

RPA 是一个 48 位（6 字节）的蓝牙随机地址，其内部被分为两个功能区域：

▸ 地址位布局（MSB → LSB，即 addr[5] → addr[0]）
bit 47:46
0b01
bit 45:24 — prand[21:0]
随机数（22 位）
bit 23:0 — hash[23:0]
AES hash（24 位）
标识位 0b01（固定，标识 RPA 类型）
prand：每次轮换随机生成的 22 位随机数
hash：ah(IRK, prand) 的低 24 位

字节级映射（实际内存布局）

蓝牙地址以 little-endian 存储，addr[0] 为最低有效字节：

字节索引内容备注
addr[0]hash[7:0]hash 最低字节
addr[1]hash[15:8]hash 中间字节
addr[2]hash[23:16]hash 最高字节
addr[3]prand[7:0]prand 最低字节
addr[4]prand[15:8]prand 中间字节
addr[5]prand[23:16]最高字节，bit7:6 固定为 0b01
⚡
易混淆点

蓝牙规范文本通常以 XX:XX:XX:XX:XX:XX 格式展示地址，其中最左侧字节是 addr[5]（高位），最右侧是 addr[0]（低位）。编程时要特别注意这与字节数组索引方向相反。

§ 04

IRK 与 ah() 函数原理

IRK（Identity Resolving Key）

IRK 是一个 128 位（16 字节）的对称密钥，在 SMP（Security Manager Protocol）配对过程中由双方设备相互交换，存储于本地安全存储（Resolving List）。它是识别对端设备真实身份的"钥匙"。

ℹ
IRK 的安全属性

IRK 具有单向性：持有 IRK 可以验证 RPA，但无法从 RPA 反推 IRK。这是因为 AES-128 在密码学意义上是不可逆的伪随机置换。

ah() 函数定义

规范定义了专用的地址哈希函数 ah(k, r)，其数学描述如下：

BT Core Spec Vol 3, Part H, §2.4.2.2 — ah 函数
ah(k, r) = e(k, r')[0:24]
其中：r' = r || 0x00000000000000000000000000 （r 后补 0 至 128 位）
e(k, x) = AES-128(k, x) （标准 AES-128 加密，k 为密钥）
取结果最低 24 bit 作为输出

算法步骤分解

01
构造 r'（填充输入）

将 24 位 prand 放入一个 128 位（16 字节）缓冲区的最低位，其余高位全部填充 0x00。得到 r'[16]。

02
字节序转换

蓝牙规范内部使用 little-endian，标准 AES 块操作使用 big-endian。必须将 IRK（k）和 r' 各自字节反转后，才能送入标准 AES 实现。

03
AES-128 加密

以反转后的 IRK 为密钥，对反转后的 r' 执行一次标准 AES-128 加密，得到 128 位密文 e。

04
提取低 24 位

在 big-endian AES 输出中，取最后 3 个字节（e[13]、e[14]、e[15]）并逆序，得到 little-endian 的 24 位 hash 值。

05
比较 hash

将计算出的 hash 与 RPA 地址中的 hash 字段（addr[0..2]）逐字节比较。完全一致则解析成功，说明此 RPA 由本 IRK 生成。

§ 05

完整解析流程

实际系统中，控制器（Controller）通常维护一个 Resolving List，其中存储了所有已配对对端的 IRK。当收到一个 RPA 广播时，解析流程如下：

①
格式检查

检查 addr[5] 高 2 位是否为 0b01（即 (addr[5] & 0xC0) == 0x40）。若不符合则非 RPA，直接跳过。

②
提取 prand 与 hash

prand = {addr[5], addr[4], addr[3]}，hash_addr = {addr[2], addr[1], addr[0]}

③
遍历 Resolving List

对 Resolving List 中每一条记录的 IRK，执行 hash_calc = ah(IRK, prand)。

④
哈希比较

若 hash_calc == hash_addr，则该 IRK 对应的设备就是 RPA 的真实身份，解析成功，返回该设备的 Identity Address。

⑤
遍历完毕未命中

若所有 IRK 均不匹配，则该 RPA 来自未知/未配对设备，或地址已损坏，返回解析失败。

💡
硬件加速

高端蓝牙控制器（如 Nordic nRF5340、TI CC2652）支持硬件 RPA 解析，Controller 层自动完成，Host 层直接收到已解析的 Identity Address。软件协议栈（如 Zephyr、NimBLE）也提供此功能的软件实现。

§ 06

代码设计与实现

以下为完整的、无外部依赖的 C 实现，包含 AES-128 软件实现、ah() 函数以及 RPA 验证逻辑。每个模块均经过单独设计，便于移植到嵌入式平台。

6.1 AES-128 纯软件实现

为保持可移植性，不依赖 OpenSSL 等外部库，自行实现 AES-128。包含密钥扩展（Key Schedule）、字节替换（SubBytes）、行移位（ShiftRows）、列混淆（MixColumns）和轮密钥加（AddRoundKey）五个子操作。

/* ── S-Box 查找表（AES 标准） ── */
static const uint8_t sbox[256] = {
    0x63,0x7c,0x77,0x7b,0xf2,0x6b,0x6f,0xc5,
    /* ... 完整 256 字节查找表 ... */
};

/* ── 轮常量（RCON） ── */
static const uint8_t rcon[11] = {
    0x00,0x01,0x02,0x04,0x08,
    0x10,0x20,0x40,0x80,0x1b,0x36
};

/* GF(2^8) 乘法 */
static uint8_t gmul(uint8_t a, uint8_t b) {
    uint8_t p = 0;
    for (int i = 0; i < 8; i++) {
        if (b & 1) p ^= a;
        uint8_t hi = a & 0x80;
        a <<= 1;
        if (hi) a ^= 0x1b;  /* GF 模多项式 x^8+x^4+x^3+x+1 */
        b >>= 1;
    }
    return p;
}

typedef struct { uint8_t rk[11][16]; } AES128_CTX;

/* 密钥扩展：生成 11 轮轮密钥 */
static void aes128_key_expand(AES128_CTX *ctx, const uint8_t key[16]) {
    memcpy(ctx->rk[0], key, 16);
    for (int i = 1; i <= 10; i++) {
        uint8_t *prev = ctx->rk[i-1], *cur = ctx->rk[i];
        cur[0]  = prev[0]  ^ sbox[prev[13]] ^ rcon[i];
        cur[1]  = prev[1]  ^ sbox[prev[14]];
        cur[2]  = prev[2]  ^ sbox[prev[15]];
        cur[3]  = prev[3]  ^ sbox[prev[12]];
        for (int j = 4; j < 16; j++)
            cur[j] = prev[j] ^ cur[j-4];
    }
}

/* AES-128 单块加密（128-bit 输入 → 128-bit 输出） */
static void aes128_encrypt_block(const AES128_CTX *ctx,
                                  const uint8_t in[16], uint8_t out[16]) {
    uint8_t s[16];
    /* Round 0: AddRoundKey */
    for (int i = 0; i < 16; i++) s[i] = in[i] ^ ctx->rk[0][i];

    for (int rnd = 1; rnd <= 10; rnd++) {
        /* SubBytes */
        for (int i = 0; i < 16; i++) s[i] = sbox[s[i]];
        /* ShiftRows：行移位 */
        uint8_t t;
        t=s[1]; s[1]=s[5]; s[5]=s[9]; s[9]=s[13]; s[13]=t;
        t=s[2]; s[2]=s[10]; s[10]=t;
        t=s[6]; s[6]=s[14]; s[14]=t;
        t=s[15]; s[15]=s[11]; s[11]=s[7]; s[7]=s[3]; s[3]=t;
        /* MixColumns（最后一轮跳过）*/
        if (rnd < 10) {
            for (int c = 0; c < 4; c++) {
                uint8_t *col = s + c*4;
                uint8_t a0=col[0],a1=col[1],a2=col[2],a3=col[3];
                col[0]=gmul(0x02,a0)^gmul(0x03,a1)^a2^a3;
                col[1]=a0^gmul(0x02,a1)^gmul(0x03,a2)^a3;
                col[2]=a0^a1^gmul(0x02,a2)^gmul(0x03,a3);
                col[3]=gmul(0x03,a0)^a1^a2^gmul(0x02,a3);
            }
        }
        /* AddRoundKey */
        for (int i = 0; i < 16; i++) s[i] ^= ctx->rk[rnd][i];
    }
    memcpy(out, s, 16);
}

6.2 ah() 函数实现

/**
 * @brief  ah(k, r) — BT Core Spec Vol 3, Part H, §2.4.2.2
 * @param  k    IRK，16字节，little-endian (index 0 = LSB)
 * @param  r    prand，3字节，little-endian
 * @param  out  输出 hash，3字节，little-endian
 */
static void bt_ah(const uint8_t k[16],
                  const uint8_t r[3],
                  uint8_t out[3])
{
    /* Step 1: 构造 r'，将 prand 放入 16 字节缓冲区低位，其余补 0 */
    uint8_t r_prime[16] = {0};
    r_prime[0] = r[0];   /* prand LSB */
    r_prime[1] = r[1];
    r_prime[2] = r[2];   /* prand MSB */

    /* Step 2: 字节反转（LE → BE），准备送入标准 AES */
    uint8_t k_be[16], r_be[16], e_be[16];
    for (int i = 0; i < 16; i++) {
        k_be[i] = k[15 - i];        /* IRK 反转 */
        r_be[i] = r_prime[15 - i];   /* r' 反转 */
    }

    /* Step 3: AES-128(k, r') */
    AES128_CTX ctx;
    aes128_key_expand(&ctx, k_be);
    aes128_encrypt_block(&ctx, r_be, e_be);

    /* Step 4: 取 BE 结果末 3 字节，逆序写出（转回 LE） */
    out[0] = e_be[15];  /* hash LSB */
    out[1] = e_be[14];
    out[2] = e_be[13];  /* hash MSB */
}

6.3 字节序处理要点

这是最容易出 bug 的地方。蓝牙规范定义的数学运算与实际内存布局之间存在字节序差异：

数据规范描述内存存储送入 AES 前
IRK（k） 128-bit 整数，MSB 在左 little-endian，k[0]=LSB 需反转：k_be[i] = k[15-i]
prand（r） 24-bit 整数，MSB 在左 little-endian，r[0]=LSB 补零后反转
AES 输出（e） 128-bit，MSB 在左 big-endian 数组 取 e[13:15]，逆序写出
RPA 地址 addr[5]:addr[0] little-endian，addr[0]=LSB —

6.4 RPA 验证主函数

/**
 * @brief  使用 IRK 验证 RPA 地址
 * @param  irk   16字节 IRK，little-endian
 * @param  addr  6字节 RPA，little-endian（addr[0]=最低字节）
 * @return true = IRK 匹配，解析成功
 */
bool bt_resolve_rpa(const uint8_t irk[16], const uint8_t addr[6])
{
    /* Step 1: 格式校验 — addr[5] 高2位必须是 0b01 */
    if ((addr[5] & 0xC0) != 0x40) return false;

    /* Step 2: 分离 prand 和 hash */
    uint8_t prand[3] = { addr[3], addr[4], addr[5] };
    uint8_t hash[3]  = { addr[0], addr[1], addr[2] };

    /* Step 3: 计算期望 hash */
    uint8_t hash_calc[3];
    bt_ah(irk, prand, hash_calc);

    /* Step 4: 常数时间比较（防侧信道）*/
    uint8_t diff = hash[0] ^ hash_calc[0]
                 | hash[1] ^ hash_calc[1]
                 | hash[2] ^ hash_calc[2];
    return (diff == 0);
}

/* ── 批量解析：遍历 Resolving List ── */
typedef struct {
    uint8_t irk[16];
    uint8_t identity_addr[6];
    uint8_t addr_type;  /* 0=public, 1=static_random */
} resolving_entry_t;

const resolving_entry_t *bt_find_identity(
    const uint8_t rpa[6],
    const resolving_entry_t *list, int count)
{
    for (int i = 0; i < count; i++) {
        if (bt_resolve_rpa(list[i].irk, rpa))
            return &list[i];
    }
    return NULL;  /* 未找到 */
}
✓
常数时间比较

使用按位或（|）代替短路逻辑（&&）进行 hash 比较，可防止计时侧信道攻击（timing side-channel）：无论数据内容如何，比较操作耗时恒定。

§ 07

安全思路与威胁模型

威胁模型概览

👁
被动追踪攻击

攻击者长期监听 BLE 广播，尝试关联同一设备的历史地址。RPA 每次轮换使地址不可关联，有效抵御此类攻击。

🔑
IRK 泄漏风险

若 IRK 被窃取，攻击者可重放解析所有历史 RPA。IRK 必须存储于 Secure Storage，设备绑定删除时应彻底清除。

⏱
地址轮换频率

轮换间隔越短隐私越好，但对合法对端的识别延迟增加。规范推荐 15 分钟，实践中部分设备采用 5~30 分钟可配置。

📡
碰撞概率

hash 仅 24 bit，理论碰撞概率约 1/2²⁴（约百万分之一）。攻击者无法从碰撞中获益：即使两个不同 IRK 产生相同 hash，设备业务层仍会通过握手拒绝伪造方。

🕵
Resolving List 侧信道

遍历 List 时，提前返回会泄露列表长度/位置信息。生产实现应使用恒定时间遍历，或硬件解析器统一处理。

🔄
重放攻击

RPA 每个轮换周期内固定，攻击者无法在本周期外重放（地址已更换）。周期内重放属于正常通信，无法带来额外权限。

安全设计原则

P1
最小暴露面原则

IRK 不应跨进程/跨网络传输，仅在本地安全存储与蓝牙控制器之间流通。Host 层不应将 IRK 明文记录到日志。

P2
防御降级攻击

部分旧设备支持关闭 RPA，退化为静态随机地址。实现时应强制要求对端使用 RPA，或明确接受的地址类型范围。

P3
配对安全绑定

IRK 通过 SMP LE Secure Connections 交换时受 ECDH 密钥协商保护（BT 4.2+）。应禁用旧版 Just Works 配对以防 MitM。

P4
密钥生命周期管理

解除配对时应同时从 Resolving List 删除对端 IRK，并清零内存中的临时副本（memset_s 或等效安全擦除函数）。

AES-128 作为 ah() 基础的安全性

使用 AES-128 而非更简单哈希（如 CRC/MD5）的原因在于：

  • 伪随机性：AES 输出与真随机不可区分（PRF 假设），使攻击者无法从 RPA 推导任何 IRK 信息
  • 密钥绑定：输出与 IRK 强绑定，不同 IRK 生成完全不同的 hash，不存在共享密钥弱点
  • 硬件普及：现代 SoC 普遍带 AES 硬件加速（ARM TrustZone CryptoCell、Intel AES-NI），计算开销极低

嵌入式平台优化建议

  • 使用 查表法（T-table） 替代 gmul() 按位运算，在 Cortex-M4 上速度可提升 3~5 倍
  • Nordic nRF5340 等芯片提供 CryptoCell-312 硬件加速，通过 nrf_cc312_lib 调用
  • 若 Resolving List 很长（10+ 条目），可采用 并行 AES 流水线 或 SIMD 指令（Cortex-A 平台的 NEON AES）
  • ROM 受限设备可使用 aes_sbox_compute() 动态计算 S-Box，以代码空间换 256 字节 ROM

使用 OpenSSL 的简化版 ah()

#include <openssl/aes.h>

/**
 * OpenSSL 版 bt_ah() — 适用于 Linux 桌面/服务器调试
 * 注意：OpenSSL AES 使用 big-endian，仍需做字节序转换
 */
void bt_ah_openssl(const uint8_t k[16], const uint8_t r[3], uint8_t out[3]) {
    uint8_t r_prime[16] = {0};
    r_prime[0] = r[0]; r_prime[1] = r[1]; r_prime[2] = r[2];

    uint8_t k_be[16], r_be[16], e_be[16];
    for (int i = 0; i < 16; i++) {
        k_be[i] = k[15-i];
        r_be[i] = r_prime[15-i];
    }

    AES_KEY aes_key;
    AES_set_encrypt_key(k_be, 128, &aes_key);
    AES_encrypt(r_be, e_be, &aes_key);

    out[0] = e_be[15];
    out[1] = e_be[14];
    out[2] = e_be[13];
}

Python 验证脚本（调试用）

from Crypto.Cipher import AES  # pip install pycryptodome

def bt_ah(irk_le: bytes, prand_le: bytes) -> bytes:
    """
    irk_le:   16-byte IRK, little-endian
    prand_le:  3-byte prand, little-endian
    returns:   3-byte hash, little-endian
    """
    # 构造 r'
    r_prime = prand_le + bytes(13)  # 补 13 个 0x00
    # 字节反转 → big-endian
    k_be = bytes(reversed(irk_le))
    r_be = bytes(reversed(r_prime))
    # AES-128 加密
    cipher = AES.new(k_be, AES.MODE_ECB)
    e_be = cipher.encrypt(r_be)
    # 取末 3 字节，逆序
    return bytes([e_be[15], e_be[14], e_be[13]])

def resolve_rpa(irk_le: bytes, rpa_le: bytes) -> bool:
    assert (rpa_le[5] & 0xC0) == 0x40, "Not an RPA"
    prand = rpa_le[3:6]
    hash_addr = rpa_le[0:3]
    hash_calc = bt_ah(irk_le, prand)
    return hash_addr == hash_calc

# 示例
irk = bytes.fromhex("0f0e0d0c0b0a09080706050403020100")
rpa = bytes.fromhex("aabbcc112273")  # 按 LE 字节序
print("Resolved:", resolve_rpa(irk, rpa))

§ 10

在 CCC 数字钥匙中的应用

CCC Digital Key（车联网联盟数字钥匙）规范深度依赖蓝牙 LE 隐私机制。RPA 在数字钥匙场景中扮演关键角色：

场景RPA 的作用相关规范
车辆广播 车辆使用 RPA 广播，仅已配对手机可识别，防止非配对设备追踪 CCC DK R3 §5.x
手机扫描 手机扫描周边 BLE 设备，用已存储的车辆 IRK 快速识别目标车辆 CCC DK R3 §6.x
被动无感进入 后台 RPA 解析完成设备识别，无需用户操作即可触发解锁流程 CCC DK R3 §7.x
数字钥匙共享 好友设备获得新 IRK 后，可独立解析车辆 RPA，无需原车主在场 CCC DK R3 §11.x
🔑
与 DK 规范的结合

CCC R3 在 BLE 层之上叠加了自己的应用层安全（ECDH + AES-GCM），但底层蓝牙隐私机制（RPA/IRK）是通信发现阶段的第一道防线。IRK 由 CCC 的 SE（Secure Element）安全保管，与数字钥匙私钥一同受到硬件安全保护。

总结

RPA 机制以极低的计算代价（单次 AES-128 运算，~1μs 量级）实现了实用的蓝牙隐私保护。其设计精妙之处在于：

  • 对称性：生成与验证使用同一 IRK 和相同 ah() 函数，无需非对称运算
  • 本地性：完全离线，不依赖任何网络服务器，天然适合车载/嵌入式场景
  • 可扩展性：一个设备可存储多个对端 IRK，支持一对多的识别关系
  • 标准化：作为蓝牙核心规范的一部分，全球所有合规蓝牙芯片均支持
