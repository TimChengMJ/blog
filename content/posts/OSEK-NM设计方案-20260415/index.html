什么是 OSEK NM？
OSEK/VDX Network Management（OSEK NM）是 OSEK/VDX 联盟（1993 年由宝马、博世、大众等联合成立）制定的汽车 CAN 网络管理标准，最终被纳入 ISO 17356-5。它定义了分布式车载 ECU 如何协调上电、维持通信和进入睡眠，是 AUTOSAR CanNm 的直接前身。今日众多量产 ECU（特别是 2010 年前的平台及低成本派生平台）仍在使用 OSEK NM。
历史沿革
为什么需要网络管理

汽车 CAN 网络中多个 ECU 共享总线，若各自独立决定何时休眠和唤醒，将引发通信冲突、暗电流超标和功能丢失等问题。OSEK NM 通过统一的逻辑机制确保所有节点同步协调。

协调唤醒
KL15 上电或总线活动触发后，所有节点按统一策略进入通信状态，避免竞争
协调休眠
所有节点在确认无通信需求后同步进入 Bus-Sleep，降低暗电流
故障检测
通过逻辑环机制检测节点超时缺失，进入 Limp-Home 容错模式
轻量高效
OSEK NM 代码体积小、确定性强，适合资源受限的 8/16 位 MCU

NM 报文类型
Alive 存活报文
节点加入网络时发送，宣告自己在线。CByte = 0x01。触发其他节点将此节点加入逻辑环
Ring 环令牌报文
逻辑环正常运转时周期传递。CByte = 0x08（纯Ring）或包含 Sleep.ind/ack 位。ScaledNodeID 填写目标节点
LimpHome 跛行报文
逻辑环故障（TMax 超时）时发出，节点进入降级模式仍维持通信。CByte = 0x02
SleepInd 睡眠意图
Ring 报文中 CByte.Sleep.ind 位置 1，告知他节点本节点希望进入休眠
SleepAck 睡眠确认
Ring 报文中 CByte.Sleep.ack 位置 1，所有节点均确认后触发 Bus-Sleep
通信需求模型
OSEK NM 通信需求：每个节点维护一个通信请求计数器。当应用层有通信需求时调用 NMInit() 或 RequestComm() 递增计数器，维持网络活跃；无需通信时调用 ReleaseComm() 递减，归零后允许进入休眠流程。这与 AUTOSAR ComM 的用户请求机制类似，但 OSEK 版本更为简洁直接。

选型建议
选 OSEK NM 的场景
· 传统 CAN 网络，无以太网需求
· MCU 资源受限（ROM < 128KB）
· 无 PNC 部分网络需求
· 已有 OSEK OS 基础的老平台
· 成本敏感的低端 ECU
选 AUTOSAR CanNm 的场景
· 全 AUTOSAR 架构平台
· 需要 PNC 精细化电源管理
· 多总线协调（CAN+ETH）
· 跨 OEM/Tier-1 互操作
· 功能安全（ISO 26262）认证项目
迁移兼容说明：AUTOSAR CanNm 在设计上兼容 OSEK NM 的基本行为概念（唤醒/休眠状态机、NM 报文触发），但报文格式、定时器参数和 API 完全不同。老 OSEK 节点和新 AUTOSAR 节点不能混接同一条 CAN NM 总线，必须通过网关进行协议转换。

数据模型：节点配置字节

OSEK NM 中每个节点维护一个 Config Byte Array（通常 8 字节 = 64 位），每一位对应一个可能存在的节点（最多 64 个）。节点在线则对应位为 1，离线则为 0。此位图通过 Ring 报文中的 User Data 字段传递，实现全网节点存活感知。

Direct Network Management
直接网络管理（Direct NM）
基于逻辑令牌环的去中心化协调机制
Direct NM 核心思想：所有节点按 Node-ID 升序排列形成逻辑环（0 → 1 → 2 → … → N → 0）。每个节点持有逻辑"令牌"时，向后继节点发送 Ring 报文，并等待来自前驱节点的 Ring 报文。通过令牌流转实现分布式协调，无需中央管理节点。
逻辑环工作原理
Direct NM 关键行为规则
R1
发送 Ring 的条件
节点收到来自逻辑前驱（本节点 ID 的前一个在线节点）的 Ring 报文后，才向自己的逻辑后继发送 Ring 报文
R2
目标地址写入规则
Ring 报文的 ScaledNodeID 字段填写目标节点（后继）的 Node-ID。若目标节点不存在（离线），则写下一个在线节点的 ID，跳过离线节点
R3
TTyp 超时重发
若在 TTyp 时间内没有收到前驱节点的 Ring，等待 TMax 超时后判定前驱离线，更新逻辑环，向新的前驱发出等待，或进入 Limp-Home
R4
最低 Node-ID 节点启动环
网络刚启动时，Node-ID 最低的在线节点负责发出第一个 Ring 报文，启动令牌传递
R5
Alive 后加入逻辑环
新节点上电时先发送 Alive 报文，其他节点收到 Alive 后将其插入本地逻辑环中，从下一圈令牌传递开始包含新节点
Direct NM 的优势与局限
✅ 优势
· 自发现：节点动态加入/离开
· 故障可见：通过 Ring 断环检测节点故障
· 无中心节点：任意节点故障不影响其他节点通信
· 实现简单：状态机紧凑，资源占用少
⚠️ 局限
· 延迟不确定：令牌传播延迟随节点数线性增加
· 节点数限制：逻辑环最大 64 节点
· 配置字节带宽：Ring 携带的配置字节受 8 字节帧限制
· 不支持 PNC：无部分网络能力
Indirect Network Management
间接网络管理（Indirect NM）
基于总线活动感知的简化 NM 机制
Indirect NM 核心思想：节点不发送专用 NM PDU，而是通过监听总线上任意 CAN 报文的活动来判断网络是否需要保持激活。只要总线上有报文在传输，节点就认为网络活跃并重置超时定时器。总线静默超过 TMax 后，节点进入 Bus-Sleep。
Indirect NM 特点
无专用 NM 报文
不发送 Alive / Ring / LimpHome，NM 状态完全依赖监听普通应用报文的总线活动
实现极简
代码量极少（<1KB ROM），无需 Node-ID 分配，适合传感器/执行器类简单节点
无故障诊断能力
无法区分"网络无需求"与"节点故障"，不能检测特定节点是否在线
被动参与
完全被动，只监听不主动协调，适合不需要主动参与 NM 协调的从节点

Direct vs Indirect 适用场景
场景推荐模式原因
网关、BCM、ECM 等核心 ECUDirect NM需要主动参与网络协调，发现节点故障
温湿度传感器、光传感器Indirect NM只需感知总线活动，无需主动协调
车窗控制模块（简单执行器）Indirect NM资源受限，只需被唤醒和休眠
TCU、ABS、ESP 等安全系统Direct NM需要明确的节点存活检测和容错能力
诊断接口节点（网关侧）Direct NM需控制整网进入诊断状态
State Machine
OSEK NM 状态机详解
Direct NM 完整状态转换（ISO 17356-5 定义）
状态机概述：OSEK Direct NM 定义了 4 个主状态（NMOff、BusSleep、NMInit、NM）和 NM 内部的子状态（Alive、Ring、LimpHome）。状态转换由应用层调用、定时器超时和总线活动共同驱动，由 NMMainFunction() 在 OS 周期任务中推进。

BusSleep收发器关闭，CAN 完全休眠，MCU 进入低功耗模式无总线活动检测 / KL15 唤醒
NMInit节点初始化，向网络发送 Alive 报文，等待其他节点响应Alive发送 Alive 后自动进入 NM 模式
Alive发出 Alive 后等待逻辑环建立，等待前驱节点的 Ring 报文Alive收到前驱 Ring → 进入 Ring 状态
Ring正常运行：收到前驱 Ring → 发出自己的 Ring 给后继RingTMax 超时进入 LimpHome；SleepAck 进入 BusSleep

Timers & Parameters
定时器与关键参数
OSEK NM 定时器定义及典型值
定时器总览
定时器符号典型值作用超时行为
TTypTypical Time10msRing 令牌传递的典型周期。节点收到前驱 Ring 后，等待 TTyp 内发出自己的 Ring进入等待前驱 Ring 的超时监控
TMaxMaximum Time100ms等待前驱 Ring 的最长时间。超过则判定前驱节点离线，触发逻辑环重构更新逻辑环 → Limp-Home / 跳过离线节点
TWbsWait Bus Sleep Time10ms全网 SleepAck 确认后，等待总线完全安静再进入 Bus-Sleep 的时间进入 Bus-Sleep 状态
TErrorError Timer200msLimpHome 状态下等待逻辑环恢复的最大超时继续维持 LimpHome（OEM 定义处理策略）
定时器关系约束：
· TTyp 必须小于 TMax：TTyp < TMax（否则单个节点的令牌传递就会触发超时）
· TMax 设置需考虑最大节点数：TMax ≥ N × TTyp（N 为网络节点数，确保令牌绕一圈的时间内不超时）
· TWbs 应足够短，避免总线长时间在 Prepare 状态消耗电流（通常 10~50ms）

Design Methodology
设计方式
OSEK NM 工程化设计流程与最佳实践
整体设计流程
01
网络节点规划
梳理 CAN 网络中所有 ECU，确定哪些需要 Direct NM（主动参与），哪些使用 Indirect NM（被动监听）
02
Node-ID 分配
为每个 Direct NM 节点分配唯一的 Node-ID（0x00~0x3F，最多 64 个）。ID 决定逻辑环的排列顺序，低 ID 优先。建议按功能域分段分配，便于维护
例：BCM=0x01, GW=0x02, ECM=0x03, TCU=0x04 ...
03
CAN ID 规划
OSEK NM 报文的 CAN ID 通常为 0x400+NodeID（11位标识符）。每个节点有独立的 NM CAN ID，全网规划时需避免冲突。基址（0x400）可由 OEM 定义
04
定时器参数设计
根据网络节点数和 OEM 时间预算计算：TMax ≥ N × TTyp（N = 最大节点数）。考虑休眠响应时间要求设置 TWbs
05
通信需求建模
为每个应用功能定义通信请求：哪些功能需要调用 RequestComm()，哪些在完成后立即 ReleaseComm()，以优化整网休眠时机
06
OS Task 设计
NMMainFunction() 必须由 OSEK OS 的周期 Task 调用，调用周期 = TTyp / N（保证足够的分辨率）。通常配置为 1ms 或 5ms 周期 Task
07
中断与唤醒源配置
配置 CAN 收发器的总线唤醒中断，确保 Bus-Sleep 状态下总线活动能触发 MCU 唤醒中断，进而调用 NMInit()
08
集成测试验证
通过 CAN 分析仪抓包验证：Ring 令牌传递时序、Alive 报文正确性、Sleep 协调过程、Limp-Home 触发和恢复行为
常见设计错误
错误现象解决方案
TMax 设置过小节点频繁误判前驱离线，进入 Limp-Home，网络不稳定确保 TMax ≥ N × TTyp，留出 20% 余量
Node-ID 冲突两个节点 ID 相同，逻辑环死锁或消息冲突在 NM 初始化时加入 ID 校验逻辑，上电自检
NMMainFunction 调用不及时定时器分辨率不足，TTyp 超时误差过大调用周期 ≤ TTyp / 10，建议 1ms 精度
未处理 NMOff → BusSleep 路径强制关闭 NM 时，其他节点仍等待此节点 Ring先发送 SleepInd 参与协调，再 NMOff
Indirect 节点误配置 CAN ID占用了 Direct NM 的 CAN ID 空间，导致报文冲突Indirect 节点不发 NM PDU，确保无 CAN ID 占用
Model & Configuration
模型配置方式
OSEK NM 配置文件结构与代码生成
OIL 文件配置（OSEK Implementation Language）

OSEK 系统通过 OIL（OSEK Implementation Language）文件进行静态配置。NM 的配置在 OIL 文件的 NM 和 NMNODE 块中定义，由代码生成工具（如 ProOSEK、ETAS RTA-OSEK、ARCTCORE）读取并生成 C 代码。

/* OIL 文件 NM 配置示例 */

NM nm_can1 {
    NMTYPE = DIRECT;               /* 选择 Direct NM 模式 */
    CANBUSID = can_channel_1;      /* 绑定 CAN 通道 */
    IDENTBASE = 0x400U;            /* NM 报文 CAN ID 基址 */
    TTYP = 10U;    /* ms - 典型定时器 */
    TMAX = 100U;   /* ms - 最大超时 */
    TWBS = 10U;    /* ms - 等待总线睡眠 */
};

NMNODE bcm_node {
    NM     = nm_can1;
    NODEID = 0x01U;                /* 本节点 ID */
    NMTYPE = DIRECT;
    NMSTARTUPTYPE = NORMAL;        /* NORMAL / APPLICATIONSTART */
    RXOBJECT = nm_rx_msg;         /* NM 接收消息对象 */
    TXOBJECT = nm_tx_msg;         /* NM 发送消息对象 */
};

Logical Ring
逻辑环结构详解
逻辑环的建立、维护与重构
逻辑环建立过程
①
上电广播 Alive
各节点上电后发送 Alive 报文（CByte=0x01），宣告自己加入网络。ScaledNodeID 填写自身 ID
ALL: TX Alive [ScaledNodeID=selfID, CByte=0x01]
②
收集在线节点
每个节点收到他节点的 Alive 后，将其 Node-ID 写入本地 Config Byte Array 对应位，建立本地在线节点视图
③
最低 ID 启动环
节点 ID 最低的在线节点（通常 BCM 或 GW）负责发出第一个 Ring 报文，目标写入次低 ID 节点，启动令牌传递
Node_0x01: TX Ring [ScaledNodeID=0x02, CByte=0x08]
④
Ring 令牌传递
0x02 收到 Ring 后发给 0x03，0x03 发给 0x04 … 0xFF 发给 0x01，完成一圈令牌传递
⑤
Config Byte 同步
Ring 报文携带发送节点的 Config Byte Array，接收方合并后继续传递，最终全网每个节点都有完整的在线节点视图
节点离线处理（逻辑环重构）
A
检测超时
节点 C（0x03）等待前驱 B（0x02）的 Ring，超过 TMax 无响应，判定 B 已离线
B
更新本地环
C 从本地 Config Byte Array 中清除 B 的位，将 B 的前驱 A（0x01）设为新的前驱
C
发送 LimpHome 或继续 Ring
若环中还有其他节点，C 直接发出 Ring（跳过 B）；若 C 是最后一个节点，进入 LimpHome 状态
D
D
全网同步离线信息
C 的 Ring 中不再包含 B 的存活位，其他节点收到后同步更新本地视图
节点重新加入（动态加入）
节点 B 复位重启后发送 Alive 报文，其他节点收到后将 B 插入逻辑环（在 B 的前驱和后继之间），从下一圈 Ring 传递开始包含 B。这是 OSEK NM 区别于 AUTOSAR CanNm 的重要特性——完全动态的节点管理，无需预配置节点列表。

必要配置项
配置项类型约束说明
NodeIDuint80x00~0x3F，全网唯一逻辑环排序依据，也是 Config Byte 位图中的偏移

配置一致性要求
整网配置约束（必须保证）：
· 所有 Direct NM 节点的 TTyp 和 TMax 必须使用完全相同的值（由 OEM 在系统规格书中统一定义）
· NodeID 在同一 CAN 网络内唯一，不可重复
· IDENTBASE 在整条总线上统一，所有节点使用相同基址
· 若同一总线混用 Direct 和 Indirect NM，Indirect 节点不发任何 NM PDU，确保不占用 0x400~0x43F 的 CAN ID 空间
Wake-up Flow
唤醒流程
节点从 Bus-Sleep 到 Ring 状态的完整过程
唤醒触发源
KL15 上电唤醒
点火信号接通，ECU 上电，应用层调用 NMInit() 启动 NM，发送 Alive 广播全网
总线活动唤醒
CAN 总线出现隐性→显性跳变，收发器唤醒 MCU。MCU 中断服务程序调用 NMWakeupIndication()，触发 NMInit
内部事件唤醒
RTC 定时、LIN 主节点指令等内部事件触发 MCU 唤醒，应用层主动调用 NMInit
唤醒完整流程
1
MCU 从低功耗状态唤醒
硬件中断（CAN 总线活动 / KL15 / RTC）触发 MCU 从 Sleep 模式退出，初始化时钟和外设
2
CAN 收发器使能
应用层驱动代码使能 CAN 收发器（Transceiver Normal 模式），CAN 控制器开始工作
3
NMInit() 调用
应用层调用 NMInit()，NM 从 BusSleep/NMOff 切换到 NMInit 状态
NMInit(NM_CAN1)
4
发送 Alive 报文
NM 立即发送 Alive 报文（CByte=0x01），广播自身存在。同时启动 TTyp 定时器等待逻辑环建立
TX: [CAN ID=0x401, Byte0=0x01, Byte1=0x01, Byte2~7=Config]
5
其他节点收到 Alive 更新环
已在 Ring 状态的节点收到新节点的 Alive，将其插入本地逻辑环，下一圈 Ring 携带新节点信息
6
新节点收到前驱 Ring
新节点收到逻辑前驱的 Ring 报文，进入 Ring 状态，正式成为逻辑环成员，开始发送自己的 Ring
7
NMNetworkMode() 回调
NM 调用 NMNetworkMode() 通知应用层网络已就绪，应用层可以开始正常通信
Sleep Flow
休眠流程
协调休眠的完整过程与 Sleep 位传播机制
OSEK 休眠协调机制
Sleep 协调核心：OSEK NM 的休眠通过 Ring 报文中的 Sleep.ind 和 Sleep.ack 位在逻辑环中传递协调。当所有节点都将 Sleep.ind 置 1 并在 Ring 中传播后，节点开始置 Sleep.ack，全网 Sleep.ack 均置 1 后等待 TWbs 超时进入 Bus-Sleep。
休眠完整流程
1
应用层释放通信
所有应用功能完成后调用 ReleaseComm()，通信请求计数器归零，NM 允许发起休眠
App: ReleaseComm(NM_CAN1)
2
置位 Sleep.ind
节点在下一个 Ring 报文中将 CByte 的 Sleep.ind 位（Bit 4）置 1，宣告自己准备休眠
TX Ring: CByte = 0x18 (Ring + Sleep.ind)
3
Sleep.ind 在逻辑环中传播
其他节点收到含 Sleep.ind=1 的 Ring 后，若自己也准备休眠，则在转发 Ring 时也置 Sleep.ind=1。若某节点不准备休眠（有通信需求），则清除 Sleep.ind，传播被打断
4
全网 Sleep.ind 确认
当某节点收到前驱的 Ring 中 Sleep.ind=1 且自己也已 Sleep.ind=1，则认为前驱同意休眠，开始置 Sleep.ack
5
Sleep.ack 传播
Sleep.ack 同样在 Ring 中传播，每个节点收到全环 Sleep.ack=1 后，准备进入 Bus-Sleep
TX Ring: CByte = 0x38 (Ring + Sleep.ind + Sleep.ack)
6
TWbs 等待
节点停止发送 Ring，启动 TWbs 定时器，等待总线完全安静（无任何 CAN 帧活动）
7
进入 Bus-Sleep
TWbs 超时后，关闭 CAN 收发器，MCU 进入低功耗模式，NM 回调 NMBusSleepMode() 通知应用层
NMBusSleepMode() → App 保存数据 → MCU Sleep
休眠被中断的情况
休眠中断条件：若在 Sleep.ind / Sleep.ack 传播过程中，任何节点收到新的通信请求（RequestComm() 被调用），该节点立即清除 Sleep.ind，在 Ring 中发布"不睡眠"意图，整个休眠协调过程被中断，所有节点恢复到 Normal Ring 传递状态。
Limp-Home
Limp-Home 处理
逻辑环故障降级运行机制
Limp-Home 触发条件
逻辑环中断
节点等待前驱 Ring 超过 TMax，判定前驱离线，若尝试重构后仍无响应则进入 Limp-Home
单节点网络
网络中只剩下当前节点一个在线，无前驱/后继可发 Ring，直接进入 Limp-Home 自循环
CAN 总线故障
总线持续错误（Bus-Off），无法收发报文，节点进入 Limp-Home 等待总线恢复
Limp-Home 行为
L1
停止 Ring 发送
节点不再参与令牌环传递，停止等待前驱 Ring
L2
周期发送 LimpHome 报文
节点以 TTyp 为周期发送 LimpHome 报文（CByte=0x02），表明自己在线但逻辑环故障
TX LimpHome: [ScaledNodeID=selfID, CByte=0x02]
L3
监听总线恢复
若收到其他节点的有效 Ring 报文（CByte Bit 2 = 1），则重新建立逻辑环，退出 Limp-Home 回到 Ring 状态
L4
应用层通知
NM 调用 NMLimpHome() 回调通知应用层当前处于降级运行模式，应用层可选择限制部分功能
多节点同时 Limp-Home 的恢复
若多个节点同时进入 Limp-Home（如总线恢复后），各节点仍会持续发送 LimpHome 报文。Node-ID 最低的节点会首先尝试重建逻辑环，发出第一个 Ring 报文（将 CByte 中 Ring 位置 1），其他节点收到后依次退出 Limp-Home 重新加入令牌环。

Application Scenarios
典型应用场景
OSEK NM 在实际车型项目中的应用
场景一：BCM 为主控的低成本平台
背景：A 级车，仅一条 CAN 总线（舒适 CAN），ECU 数量 5~8 个，均使用 OSEK RTOS。
NM 设计：全部节点配置 Direct NM，BCM 分配最低 Node-ID（0x01）作为环的启动者。KL15 上电后 BCM 发出第一个 Alive，5 个节点在 30ms 内完成逻辑环建立，进入 Ring 状态。
优势：代码体积 <4KB，定时器精度要求低，无需额外配置工具，开发周期短。
场景二：多 ECU 网络的故障降级
背景：动力 CAN 网络，ECM / TCU / ABS / ESP 等 6 个节点，某 ECU（如 TCU）发生临时供电中断。
NM 行为：TCU 离线后 TMax 超时，ABS 检测到 Ring 断链，更新逻辑环跳过 TCU，发出 LimpHome。其他节点收到 LimpHome 同步更新。TCU 重启后发送 Alive，网络在一圈 Ring 时间内恢复。
关键：整个故障检测和恢复过程不超过 TMax + 一圈 Ring 时间（<200ms），满足功能安全要求。
场景三：OBD 诊断期间保持网络
背景：诊断仪连接，需要读取所有 ECU 的 DTC，不能让网络进入 Bus-Sleep。
NM 行为：诊断层调用 RequestComm() 保持通信请求，任何节点发起的 Sleep.ind 都会被该节点阻断。诊断完成后调用 ReleaseComm()，允许休眠流程重新启动。
注意：OSEK 平台通常由 COM 层或 NM 直接在诊断功能开启时置 RequestComm，无需应用层额外处理。
场景四：遥控器唤醒部分功能
背景：用户使用遥控器解锁，仅需激活 BCM 和车门控制器，发动机系统不需要唤醒。
NM 行为（OSEK 局限）：OSEK NM 不支持 PNC，无法选择性唤醒节点。收到 Alive 广播后，所有 Direct NM 节点均会唤醒。在 OSEK 平台上通常通过应用层逻辑控制实现：BCM 唤醒后通过应用报文通知发动机相关 ECU 是否需要完全激活，NM 层统一管理唤醒。
场景五：OSEK 向 AUTOSAR 迁移
背景：老平台 ECU 使用 OSEK NM，新平台 ECU 使用 AUTOSAR CanNm，需要在同一总线共存。
解决方案：两套 NM 不能混用同一套报文格式。通常做法是：①网关 ECU 同时实现 OSEK NM 和 AUTOSAR CanNm，负责协议转换；②在新老平台切换期间，使用兼容层将 OSEK Ring 映射为 AUTOSAR NM 的状态变化；③最终完全迁移到 AUTOSAR 后，退役 OSEK NM 代码。
