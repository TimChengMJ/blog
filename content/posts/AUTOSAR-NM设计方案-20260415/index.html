什么是 AUTOSAR NM？
AUTOSAR Network Management（NM）是 AUTOSAR 基础软件（BSW）的标准化网络管理模块，负责协调整车 ECU 节点的上电唤醒、通信建立、进入休眠和异常检测。它通过定义统一的状态机、报文格式和定时器，使不同 OEM 和 Tier-1 的 ECU 可以在同一网络中协调工作，无需专有协议。
为什么需要网络管理

现代汽车包含数十至上百个 ECU，它们通过 CAN、LIN、FlexRay 或以太网互联。如果每个 ECU 独立决定何时睡眠和唤醒，将产生：

⚡
暗电流超标
部分 ECU 无法进入睡眠，持续消耗电流，导致蓄电池亏电
🔄
通信竞争
节点各自决定休眠时机，导致报文丢失或总线冲突
🔗
唤醒失败
某节点已休眠，无法响应其他节点的请求，造成功能失效
🛡
诊断障碍
诊断仪无法预判 ECU 状态，导致诊断失败或 DTC 误报
AUTOSAR NM 的核心价值
协调唤醒与休眠
通过 NM 报文和状态机确保所有节点同步进入 Sleep/Active
总线负载管理
网络安静后统一关闭通信，降低 EMI 和功耗
部分网络（PNC）
仅激活所需的 ECU 子集，实现精细化电源管理
主动/被动模式
无通信需求的节点可进入被动模式，节省资源

NM 节点类型
Active Node 主动节点
发送 NM 报文，参与网络协调。有通信需求时必须是 Active。典型：BCM、GW、TCU
Passive Node 被动节点
只接收不发送 NM 报文，监听网络状态。无需主动参与协调的 ECU（如某些传感器）
Coordinator 协调节点
跨总线/跨通道的网络管理协调者，通常是网关 ECU（GW）。负责同步多条总线的休眠
Remote Node 远端节点
同一网络中的其他参与者，本地节点通过收到其 NM PDU 来感知其状态
通信模式三态

ComM 模块将 ECU 的通信能力划分为三种模式，由上层应用通过 ComM_RequestComMode() 切换：

模式NM 发送应用报文描述
Full Communication✅ 发送✅ 正常完整通信，节点活跃参与网络
Silent Communication❌ 停止❌ 停止发送只接收，网络安静阶段过渡
No Communication❌ 停止❌ 停止完全关闭，Bus-Sleep 状态
唤醒源分类
总线唤醒
CAN 总线出现活动（隐性→显性跳变），触发硬件唤醒中断，ECU 重新上电
内部唤醒
ECU 内部事件（RTC 定时、诊断请求、KL15 上电），无需总线活动触发
NM PDU 唤醒
收到其他节点的 NM 报文，因总线已活跃而触发自身进入 Active 状态
PNC 唤醒
PNC 位向量请求特定部分网络激活，仅唤醒相关节点子集

State Machine
网络管理状态机
CanNm / UdpNm 完整状态转换（ISO 17356-5 / AUTOSAR SWS CanNm）
状态机概述：AUTOSAR NM 状态机定义了节点在网络中的行为模式。每个节点独立维护自己的状态机，通过发送/接收 NM PDU 和定时器超时驱动状态转换。状态机统一由 CanNm_MainFunction() 在 OS Task 中周期调用推进。
各状态详解
状态行为退出条件典型耗时
Bus-Sleep 节点完全休眠，CAN 收发器关闭，NM 停止运行 检测到总线活动 / KL15 上电 / 内部唤醒 不定（直到唤醒）
Repeat Message 节点发送 NM PDU（含 Repeat 位=1），其他节点检测到此报文时也进入 Repeat 状态 NM-Repeat-Message-Timer 超时 20~200ms（OEM定义）
Normal Operation 节点有通信需求，周期发送 NM PDU，保持网络活跃 上层调用 NetworkRelease() 运行期间持续
Ready Sleep 节点释放网络需求，停止发送 NM PDU，等待 NM 超时 NM-Timeout 超时 / 收到他节点 Repeat 报文 NM-Timeout（通常≤1s）
Prepare Bus-Sleep 所有节点已进入 Ready Sleep，等待总线完全安静 WaitBusSleep Timer 超时 10~100ms

ComM 模式请求流程

应用软件组件（SW-C）通过 RTE 向 ComM 发起模式请求，ComM 汇总所有用户的请求后决定总线模式，再调用 NM 接口保持或释放网络。

01
SW-C 发起请求
应用组件调用 Rte_Call_ComM_UserRequest(ComM_FULL_COM)，请求 Full Communication
02
ComM 汇总用户请求
ComM 检查该 Channel 上所有用户的请求，任一用户请求 FULL 则维持 Full；所有用户释放则可进入 SILENT
03
ComM → Nm 发起网络请求
ComM 调用 Nm_NetworkRequest(NetworkHandle)，Nm 层转发至具体协议（CanNm）
CanNm: Bus-Sleep → Repeat Message State
04
NM 通知 ComM 网络已激活
CanNm 状态进入 Network Mode 后，回调 Nm_NetworkMode() → ComM 收到通知 → 开启 Full Communication
05
SW-C 释放通信需求
应用完成通信后调用 Rte_Call_ComM_UserRequest(ComM_NO_COM)
06
ComM 检查并释放网络
若所有用户均释放，ComM 调用 Nm_NetworkRelease()，CanNm 进入 Ready Sleep
07
Bus-Sleep 通知
NM 超时后 CanNm 进入 Bus-Sleep，回调 Nm_BusSleepMode() → ComM 切换到 No Communication
Inhibit 抑制机制
ComM Inhibit：当 ECU 需要禁止总线唤醒时（如工厂模式、运输模式），可设置 ComM Inhibit，阻止上层的 Full Communication 请求生效。分为 Wake-up Inhibition（阻止唤醒）和 Mode Limitation（限制模式切换）两种。

CanNm 详解
AUTOSAR SWS CanNm · ISO 11898 · 适用于 CAN 和 CAN FD 网络
CanNm 特性
分布式策略
所有节点平等参与，无中心协调者（除非配置 NM Coordinator）。每个节点独立运行状态机
NM PDU 广播
NM PDU 发送至广播或多播 CAN ID，所有节点均可收到并更新本地的远端节点存活信息
Node Detection
通过接收各节点 NM PDU 中的 Source NID，维护在线节点位图（NM Node Detection Bit Array）
PN 支持
支持部分网络（Partial Network），CBV Bit 4 置 1 时 User Data 携带 PNC 请求位图

CanNm 主函数调用
/* CanNm 主函数，需在 OS Task 中周期调用，周期 = CanNmMsgCycleTime */
void CanNm_MainFunction(void)
{
    /* 1. 推进状态机（定时器递减，检测超时） */
    CanNm_Internal_StateTransition();

    /* 2. 若在 Network Mode 且发送定时器到期，发送 NM PDU */
    if (CanNm_Internal_IsTxTimerExpired()) {
        CanNm_Internal_TransmitNmPdu();
    }

    /* 3. 更新 Remote Sleep Indication 检测 */
    CanNm_Internal_UpdateRemoteSleepInd();
}
Protocol Variant
UdpNm 详解
AUTOSAR SWS UdpNm · 以太网车载网络管理
UdpNm 与 CanNm 的主要差异
特性CanNmUdpNm
传输载体CAN / CAN FDUDP/IP over Ethernet
PDU 大小8 字节（固定）可变（8~64 字节）
NM 报文寻址广播 CAN IDUDP 多播（224.x.x.x）
带宽受 CAN 总线限制（1Mbps）100Mbps / 1Gbps
PNC 支持支持（受字节数限制）支持（User Data 更大）
NM-Msg-Cycle通常 10~20ms通常 100~1000ms
协调复杂度中高（需 VLAN + SOME/IP 配合）
UdpNm 典型配置：在以太网 backbone 上，UdpNm 报文发送至组播地址（如 224.0.0.1:36200），所有 VLAN 内节点订阅该组播组。NM 协调节点（通常是中央网关）同时运行 CanNm（接 CAN 子网）和 UdpNm（接以太网），桥接两种网络的唤醒/休眠决策。
DoIP 与 NM 的关系

车载以太网场景中，DoIP（Diagnostics over IP）负责诊断通信，UdpNm负责网络管理。DoIP 流量不参与 NM 状态决策，但诊断激活时 ComM 会保持 Full Communication，防止 NM 触发休眠。

Protocol Variant
LinNm / FrNm
LIN 网络管理与 FlexRay 网络管理简介
LinNm
LinNm 特点：LIN 网络是主从结构，网络管理由 LIN Master（通常是 BCM）统一控制。LinNm 极为简化：Master 决定 LIN 集群的唤醒与休眠，Slave 节点通过 LIN Sleep Command（LD_ASSIGN_NAD/LD_CONDITIONAL_CHANGE）进入睡眠，无需独立 NM PDU。LinNm 仅向 NM Interface 提供标准回调（NetworkMode / BusSleepMode），上层 ComM 无需感知底层差异。
FrNm
FrNm 特点：FlexRay 网络管理基于 TDMA 调度，NM 报文在专用 NM Slot 中传输。节点在 Active 状态下周期占用 NM Slot 发送向量（NM Vote），当所有节点的 Vote 都表示可休眠时，整网协调进入睡眠。FrNm 的休眠协调比 CanNm 更精确，但 FlexRay 在新平台中逐渐被 CAN FD + Ethernet 取代，FrNm 主要存在于老平台中。
Design Methodology
设计方式
AUTOSAR NM 工程化设计流程与最佳实践
NM 设计整体流程
01
网络拓扑分析
梳理整车 CAN / LIN / ETH 网络拓扑，确定各总线上的节点数量、节点类型（Active/Passive/Coordinator）和网关连接关系
02
NM Node ID 分配
为每条 CAN 总线上的每个 Active 节点分配唯一的 Source Node ID（0x01~0xFE）。Node ID 规划需考虑调试便利性（通常按 ECU 功能域分段）
例：BCM=0x01, GW=0x02, TCU=0x03, ...
03
唤醒源设计
确定每个 ECU 的唤醒源（KL15、KL30、总线唤醒、内部 RTC 等），设计唤醒滤波逻辑，防止误唤醒
04
PNC 规划
按功能域划分 PNC（如 PNC 0=娱乐系统、PNC 1=ADAS、PNC 2=车窗控制），定义哪些 ECU 属于哪些 PNC，设计 PNC 请求位图分布
05
定时器参数设计
根据网络负载、OEM 规范和休眠响应时间要求，设计 NM-Timeout、NM-Repeat-Msg-Time、WaitBusSleep 等定时器值
06
协调节点设计
在跨总线场景中，设计网关 ECU（GW）的 NM Coordinator 策略：哪条总线先协调，协调超时如何处理
07
AUTOSAR 工具链配置
使用 Vector DaVinci / EB tresos / ETAS ISOLAR 等工具完成 NM 模块的 ARXML 配置，生成代码
08
集成验证
通过 HIL/SIL 仿真和整车联调验证唤醒时间、休眠可靠性、PNC 精度和暗电流指标
常见设计错误
错误现象解决方案
NM-Timeout 设置过小节点频繁进入 Ready Sleep / Bus-Sleep，通信不稳定确保 NM-Timeout ≥ 3×NM-Msg-Cycle-Time
未配置 Msg-Cycle-Offset多个节点同时发送 NM PDU，CAN 总线冲突率高为每个节点设置不同 Offset，错开发送窗口
被动节点错配为主动网络无法正常休眠（该节点一直发 NM PDU 保持总线活跃）核查节点类型，PassiveMode=True 的节点不发 NM
PNC 位映射错误唤醒错误的 ECU，或目标 ECU 未被唤醒重新核对 PNC 位图与 ECU 对应关系
协调节点未同步休眠部分总线休眠，部分总线持续活跃，暗电流超标检查 NM Coordinator 的 Cluster 配置和同步逻辑

Network Coordination
网络协调机制
跨总线 NM 协调与多网关场景
为什么需要 NM 协调

整车通常有多条 CAN 总线（动力、底盘、舒适、ADAS 等），各总线通过网关（GW）连接。若各总线独立管理休眠，可能出现：

  • CAN-A 已休眠，但 CAN-B 的节点还在唤醒 CAN-A 上的节点
  • 网关无法确定何时可以关闭两条总线之间的转发
  • 部分总线长时间无法进入 Bus-Sleep，导致暗电流超标
NM Coordinator 工作原理
①
各总线 NM 独立运行
每条总线上的 CanNm 状态机独立工作，各节点进入 Ready Sleep 后 NM-Timeout 超时
②
GW 检测各通道 Remote Sleep
网关 NM Coordinator 监控所有通道的 Remote Sleep Indication。当某条总线所有节点都进入 Ready Sleep，GW 收到 Nm_RemoteSleepIndication()
③
协调休眠决策
GW 等待所有通道都收到 Remote Sleep Indication 后，在 NM PDU 的 CBV 中置 NM Coord Sleep Ready (Bit 2)，通知各总线可以协调休眠
CBV.Bit2 = 1 → "协调休眠已准备好"
④
各总线同步进入 Prepare Bus-Sleep
各总线节点收到协调信号后同步进入 Prepare Bus-Sleep → 等待 WaitBusSleep 超时 → Bus-Sleep
协调簇配置
Coordination Cluster：AUTOSAR 通过 CanNmCoordClusterIndex 将多个 NM 通道分组为一个"协调簇（Cluster）"。同一 Cluster 内的所有通道必须全部准备好后才能协调休眠。不同 Cluster 可独立休眠（用于整车分区管理）。

Partial Network Cluster
部分网络 PNC
精细化唤醒控制 — 只唤醒需要的 ECU
PNC 概念

Partial Network Cluster（PNC）是 AUTOSAR R4.0 引入的部分网络管理机制，允许整车在不唤醒所有 ECU 的前提下，只激活特定功能域所需的节点子集，大幅降低待机功耗。

PNC 工作原理
1
PNC 请求位图
每个 PNC 对应 NM PDU User Data 中的一个 bit（最多 8×6=48 个 PNC）。当某功能需要激活时，对应 PNC bit 置 1 并广播至总线
2
ECU 过滤 PNC 位
每个 ECU 配置了它关心的 PNC 集合（PNC Mask）。收到 NM PDU 后，ECU 检查 User Data 中是否有自己关心的 PNC bit=1
3
选择性激活
若 PNC bit 匹配，ECU 请求 Full Communication；若所有关心的 PNC bit=0，ECU 可保持 Bus-Sleep 状态
PNC Mask: 0b00001010 → 关心 PNC1 和 PNC3
4
CBV.PNI 位控制
发送含有 PNC 请求的 NM PDU 时，CBV.Bit4（PNI）置 1，告知接收方解析 User Data 中的 PNC 位图。否则 User Data 被视为普通用户数据
典型 PNC 分配示例
PNC ID功能域涉及 ECU唤醒条件
PNC 0动力控制ECM, TCU, ABS, ESPKL15 上电
PNC 1娱乐/信息HMI, Media, Amplifier用户触发或定时
PNC 2ADAS 功能Camera, Radar, Lidar, ADCU驾驶激活
PNC 3车身舒适BCM, Door, Seat, Climate门把手/遥控
PNC 4诊断&维护GW, BCM, ECM, TCU诊断请求
PNC Gateway（PNC-GW）：网关 ECU 在 PNC 场景中扮演聚合者角色。它在 CAN-A 上收到 PNC1 请求后，需要在 CAN-B 上发出对应的 PNC 请求，使 CAN-B 上关心 PNC1 的节点也能被唤醒——这称为 PNC Gateway（跨总线 PNC 转发）。
Application Scenarios
典型应用场景
AUTOSAR NM 在实际整车项目中的应用
场景一：KL15 上电唤醒
触发：用户转动钥匙或按下启动按钮，KL15（点火线圈）上电，向所有 ECU 提供供电信号。
流程：KL15 中断 → BCM/GW 检测到 KL15 → 发出 NM PDU（Repeat） → 总线上其他 ECU 收到 NM PDU → 各 ECU 进入 Network Mode → 应用层通信建立。
场景二：远程无钥匙进入（RKE）唤醒
触发：用户按下遥控器解锁键，BCM 通过 RF 接收信号。
NM 行为：BCM 从 Bus-Sleep 被 RF 中断唤醒 → BCM 发送 PNC 3（车身舒适）的 NM PDU → 车门、座椅等 ECU 被 PNC 3 唤醒 → 执行解锁动作 → 若无后续操作，超时后再次进入休眠。
注意：仅 PNC 3 相关 ECU 唤醒，动力系统（PNC 0）不唤醒，节省电量。
场景三：OTA 在线升级
触发：云端推送 OTA 包，TCU 收到升级指令。
NM 行为：TCU 请求 Full Communication → ComM 保持网络激活（NM 不允许进入休眠）→ 目标 ECU 接收固件包 → 升级完成后 ECU 复位 → NM 重新协调上线 → 验证成功后释放网络。
关键：OTA 期间 ComM 的 ComM_InhibitModeLimit 阻止任何 No-Communication 请求，确保升级过程不被中断。
场景四：诊断会话保持
触发：诊断仪连接 OBD 接口，发起 UDS DiagnosticSession 请求。
NM 行为：Dcm 调用 ComM_DCM_ActiveDiagnostic() 保持 Full Communication → NM 不允许进入休眠 → 诊断会话结束后 Dcm 调用 ComM_DCM_InactiveDiagnostic() → 网络可重新进入休眠流程。
场景五：整车下线检验
触发：工厂下线检验模式，需要访问所有 ECU 进行参数写入和功能验证。
NM 行为：EOL 工装启用所有 PNC → 强制所有 ECU 保持 Full Communication → 执行下线检验项目（刷写、标定、功能激活） → 检验完成后解除强制激活，网络进入正常管理模式。
